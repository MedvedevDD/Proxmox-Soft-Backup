# Recovery Orchestrator

## Назначение

Оркестратор выполняет несколько компонентов одного приложения как одну
транзакцию. Порядок компонентов берётся из `recovery_order`.

## Реализованное поведение

`execute_application_transaction()`:

1. Проверяет исходный PSB-пакет.
2. Строит план в порядке `recovery_order`.
3. Блокирует транзакции с пересекающимися путями.
4. Создаёт и проверяет один rollback-пакет.
5. Распаковывает все артефакты до остановки служб.
6. Останавливает активные службы приложения один раз.
7. Устанавливает компоненты последовательно.
8. Проверяет контрольную сумму каждого компонента.
9. Выполняет `systemctl daemon-reload` для systemd-компонентов.
10. Запускает только службы, активные до операции.
11. При ошибке возвращает заменённые каталоги в обратном порядке.

## Ограничение пересекающихся путей

Grafana пока блокируется, если одновременно требуется восстановить
`/var/lib/grafana` и `/var/lib/grafana/plugins`. Путь plugins вложен в database,
поэтому для него нужна отдельная стратегия дедупликации.

InfluxDB, Telegraf и NUT имеют независимые цели и могут выполняться текущим
транзакционным исполнителем.

## Recovery lock

Транзакция использует `schema_version: 12`. Lock содержит приложение, список
компонентов, завершённые компоненты, единый rollback-пакет, состояния служб и
итоговое состояние транзакции.

## Следующий этап

После проверки внутреннего исполнителя будет добавлен CLI-режим `--all`.

## Вложенные компоненты

Планировщик различает логический и физический порядок восстановления.

Логический порядок берётся из `recovery_order` manifest-файла. Физический
порядок рассчитывается по глубине целевых путей: родительский каталог
устанавливается раньше вложенного компонента.

Пример Grafana:

```text
Логический порядок:
configuration -> plugins -> database

Физический порядок:
configuration -> database -> plugins
```

План транзакции содержит:

- `physical_execution_order` — фактический порядок установки;
- `nested_dependencies` — связи родительских и дочерних компонентов;
- `rollback_root_components` — минимальный набор корневых компонентов для
  rollback без дублирования вложенных каталогов;
- `overlap_conflicts` — только неоднозначные конфликты, например два компонента
  с одним и тем же целевым путём.

Обычное строгое вложение больше не считается причиной блокировки. На этом
коммите меняется только планирование. Исполнитель будет переведён на физический
порядок и дедуплицированный rollback следующим коммитом.

## Исполнение вложенных компонентов

Исполнитель использует `physical_execution_order`, а не логический порядок
manifest-файла. Родительский каталог заменяется раньше дочернего.

Единый rollback-пакет создаётся только для `rollback_root_components`.
Вложенные компоненты не архивируются повторно, потому что их исходное состояние
уже содержится в родительском каталоге.

Например, для Grafana при восстановлении database и plugins:

```text
Физическая установка:
database -> plugins

Rollback roots:
database
```

Автоматический rollback по временным каталогам по-прежнему выполняется в
обратном порядке. После восстановления дочернего компонента возвращается
родительский каталог, содержащий полное исходное дерево.
